# S1-01 方案设计：压缩能力 seam 与前缀命中

> 消费已批准的 `S1-01-solution-v1` 与 `ADR-001`，只做零新增取舍的工程设计。原需求见 `S1-01_原始需求.md`。

## 1. 批准方向与设计目标

| 批准项 | 来源 | 本设计承接方式 |
|---|---|---|
| 压缩能力是 seam，两个 Adapter：`provider` 优先，`prefix` 兜底 | `S1-01-solution-v1` §4、`ADR-001` 决策 1 | §6 定 Interface 与 Adapter 集合 |
| 选择依据是 catalog 静态声明，fail-closed | 同上 | §5、§10 显式 `unsupported`，不静默降级 |
| 前缀两侧不变式，任一不成立抛 `PrefixUnavailable` | `ADR-001` 决策 2 | §2、§5、§10；坐标系由 §2 探针钉住 |
| wire body 只由 `buildChatBody()` 产出 | `ADR-001` 决策 3 | §6 I01 抽取确定性 body 构造 |
| 触发点 `min(contextWindow × threshold, contextWindow − maxTokens)` | `S1-01-solution-v1` §4 | §8、§12 断言 |
| 摘要请求沿用模型默认参数 | `ADR-001` 决策 5 | §8 参数一致性检查 |
| 上次请求体只在进程内保留 | `ADR-001` 决策 6 | §4 生命周期 |

设计目标：把上述批准项展开成可直接实施、可独立测试、可独立验收的 Interface 与文件布局；不引入新抽象层，不新增配置项。

## 2. 业务流程设计与闭合证明

```text
每轮对话
  → 会话把正常的 provider 请求发出（streamFn）
  → S1-01 旁路记录该请求的 TranscriptContext 与模型键（只存引用，不构造 body）
  → 下一轮开始前判定触发点
      ├─ 未超过 min(window × 0.95, window − maxTokens) → 继续对话
      └─ 超过 → prepareCompaction() 得到切割点与待摘要消息
                → selectTransport(model)
                    ├─ provider → requestProviderCompaction() → unsupported（显式失败，保留原上下文）
                    └─ prefix   → buildPrefixRequest() 重放上一次请求前缀 + 尾部指令
                                    ├─ 前缀校验失败 → PrefixUnavailable → 冷启动序列化分支
                                    └─ 校验通过 → 摘要调用（模型默认参数）
                → length / error → session_compact_failed（不写 entry）
                → 成功 → 写 CompactionEntry，从摘要继续
```

闭合证明：入口是「每轮开始前的触发判定」，出口是「写 entry 后继续」或「显式失败保留原上下文」。正常路径（`prefix` 命中）、显式失败路径（`provider` 未实现的 `unsupported`）、降级路径（`PrefixUnavailable` → 冷启动）、错误路径（`length`/`error`）各有一个确定下一动作，无悬空分支。

**坐标系（本设计的核心唯一映射）**：切割点定义在 session entry 坐标系，前缀定义在 transcript message 坐标系。取 `k` = `buildSessionProjection(entries).entries` 中**严格位于 `firstKeptEntryId` 所指 entry 之前**的各 entry 的 `messages.length` 之和。已用探针验证（`packages/coding-agent/test/` 临时探针，见 §17 证据）：

- 普通切割：`convertToLlm(projection.messages.slice(0, k))` 恒等于 `convertToLlm([...messagesToSummarize, ...turnPrefixMessages])`；
- 已有上次压缩时：前缀第一条是上次压缩的 `<summary>` user 消息，待摘要历史是它的**连续尾段**；
- 切在轮次中间（split turn）时：同一等式对 `messagesToSummarize + turnPrefixMessages` 成立。

由此确定一条实施约束：`previousSummary` 只出现在**尾部指令**里（`<previous-summary>`），不得作为前缀内的新消息插入；否则前缀在新请求一开始就断裂。

## 3. 业务逻辑设计与闭合证明

| 判定 | 输入 | 输出 | 不变式 |
|---|---|---|---|
| 触发判定 | `contextTokens`、`contextWindow`、`maxTokens`、`settings` | `boolean` | `enabled`；阈值 `0 < threshold < 1`；触发点严格等于 `min()` |
| 能力选择 | `model` | `TransportSelection` | 未声明 → `prefix`；声明 `provider` → `provider` |
| 前缀请求构造 | `lastRequest`、`currentContext`、`k`、`instruction` | `TranscriptContext` | 新请求消息 = `currentContext.messages.slice(0, k)` + 1 条尾部 user |
| 前缀校验 | 两次 body 的 messages 数组 | `void` | 前 `k` 条序列化后逐字节相等，否则抛 `PrefixUnavailable` |
| 摘要调用 | `TranscriptContext` + 模型默认 options | `AssistantMessage` | 不设 `max_tokens`/`reasoning` 覆盖（沿用 `createSummarizationOptions`） |

闭合证明：每个判定是纯函数或只读投影，输入来自唯一真源（§4）。`k` 的取值由 §2 的唯一映射给出，不存在第二套坐标换算。

## 4. 数据流、数据真源、数据闭环

| 数据 | 真源 | 生产者 | 消费者 | 生命周期 |
|---|---|---|---|---|
| 上一次请求的 transcript | `AgentSession` 的 `lastRequest` 字段 | `recordLastRequest` 包装的 `streamFn` | `buildPrefixRequest` | 进程内；模型键变化、工具集变化、会话重载即清空 |
| 上一次请求的 body | 无（按需派生） | `buildChatBody(last.context)`（压缩时算） | 前缀校验 | 单次压缩 |
| 切割点 `k` | `prepareCompaction` 的 `firstKeptEntryId` + `buildSessionProjection` | `compaction.ts` | `buildPrefixRequest` | 单次压缩 |
| 触发阈值 | `settings.json` → `settings-manager` | settings manager | `shouldCompact` | 配置生命周期 |
| 模型限额与能力 | catalog `contextWindow` / `maxTokens` / `compactionTransport` | 生成的模型数据 | `shouldCompact`、`selectTransport` | 静态 |
| 命中证据 | provider `usage` | 摘要调用的 usage | UI、测试、`docs/compaction.md` 记录 | 会话持久 |

依赖方向单向：`packages/coding-agent/src/core/compaction/*` → `@earendil-works/pi-ai`。body 构造只在 pi-ai 内部，coding-agent 不重新序列化。

数据闭环：`lastRequest`（引用）→ `k`（投影）→ 新请求（纯构造）→ 校验（逐字节）→ 摘要 usage → 回到 UI 与测试断言。任一处缺失都在 §10 有对应 `reason`，不会静默产生全价请求。

## 5. 状态流与控制流

```text
idle
 ├─ turn 发出 → 记录 lastRequest（引用）→ idle
 ├─ 触发点未到 → idle
 ├─ 触发 + transport=provider → failed(unsupported) → idle（上下文不变）
 ├─ 触发 + transport=prefix + lastRequest 有效 → summarizing
 │     ├─ 校验失败 → PrefixUnavailable → cold_start_serializing → summarizing
 │     ├─ length/error → failed → idle
 │     └─ 成功 → writing_entry → idle（entry 写入）
 └─ 触发 + transport=prefix + 无 lastRequest → cold_start_serializing → summarizing
```

控制流规则：
- `selectTransport` 只在触发之后执行一次，结果不缓存。
- `provider` 选择不进入任何前缀分支，也不进入序列化分支：`unsupported` 直接失败（AC5）。
- 冷启动只由 `PrefixUnavailable.no_previous` / `projection_drift` / `prefix_mismatch` 三种 `reason` 进入，且每次进入都向 UI 发出可读原因（AC6）。
- 摘要调用仍然只经过 `completeSummarization` 这一个 choke point，重试策略不变。

## 6. Module → Interface → Seam → Adapter → 文件布局

**Module A：wire body 构造（pi-ai）**

- Interface：`buildChatBody(model, context): ChatWireBody | null`。纯函数，同输入同字节；非 `openai-completions` api 返回 `null`。
- Implementation 隐藏：消息折叠（中段 system 能力、工具补丁）、工具解析、compat 解析、缓存字段。调用方不接触 compat。
- 文件：`packages/ai/src/api/openai-completions-body.ts`（从 `openai-completions.ts` 的 `buildParams` 抽出，导出 `buildOpenAICompletionsBody`）、`packages/ai/src/wire-body.ts`（按 `model.api` 分派的 `buildChatBody`）、`packages/ai/src/index.ts` 导出。
- 删除测试：删掉 `buildChatBody` 后，`openai-completions.ts` 与 `compaction/prefix.ts` 必须各自重写消息折叠与 compat 判断 → 复杂度回到两处调用方，模块成立。

**Module B：压缩传输（coding-agent，本设计的 seam）**

- Interface：
  - `selectTransport(model): TransportSelection`
  - `buildCompactionRequest(input): CompactionRequest`
  - `PrefixUnavailable`（错误类型，带 `reason`）
- 两个 Adapter（`ADR-001` 决策 1）：
  - `provider`：`requestProviderCompaction(): CompactionFailure`，本 Issue 恒返回 `unsupported`；
  - `prefix`：`buildPrefixRequest({ last, current, k, instruction }): TranscriptContext` + `assertPrefixHolds(previous, next): void`。
- Seam 位置：`compaction.ts` 的摘要请求构造处（现有 `generateSummaryWithUsage` 内部），不新增第二套调用路径。`completeSummarization` 保持唯一 LLM choke point。
- 文件：`compaction/transport.ts`（选择 + 请求构造入口）、`compaction/prefix.ts`（前缀 Adapter + 校验）、`compaction/provider-compaction.ts`（原生 Adapter 声明）、`compaction/last-request.ts`（捕获包装）、`compaction/compaction.ts`（切割点、触发、编排，收窄）。
- 删除测试：删掉 Module B 后，`compaction.ts` 必须自己判断 catalog 能力、自己切片、自己校验字节 → 复杂度回到调用方，seam 成立。

**测试面**：前缀行为只通过 `buildCompactionRequest` / `assertPrefixHolds` 与 `compact()` 的公开 Interface 验证；`k` 的映射用 `prepareCompaction` + `buildSessionProjection` 的公开输出验证，不测内部函数。

## 7. capability 级 Deep Module 调用面与执行面预算

| 调用方 | 调用的 capability | 实际执行面变化 |
|---|---|---|
| 每轮对话 | `recordLastRequest` 包装（引用赋值） | 每轮一次对象赋值，零 body 构造、零序列化 |
| 触发后 | `selectTransport` | 一次字段读取 |
| 触发后 | `buildCompactionRequest` | 一次 `slice`（数组视图，复制引用不复制文本）+ 一次 `buildChatBody`（纯计算，O(messages)） |
| 校验 | `assertPrefixHolds` | 两次 `JSON.stringify` 的消息数组比较；内存峰值 = 两次序列化，压缩是低频路径 |
| 摘要 | `completeSummarization` | 远端调用次数不变（每次压缩 1 次；split turn 仍 2 次） |

依赖面：新增依赖只有 `compaction/*` → pi-ai 的既有方向；pi-ai 内部新增 `wire-body.ts` → `openai-completions-body.ts`。不新增运行时依赖、不改 `ProviderStreams`。

回归验证方式：`npm run check` + 既有 11 个压缩测试 + 本设计新增测试；执行面以「每轮无额外 body 构造」为断言点（探针测量 `buildChatBody` 调用次数为 0）。

## 8. 输入、输出、字段值义与边界条件

| 字段 | 类型 | 值义 | 生产者 | 边界 |
|---|---|---|---|---|
| `transport` | `"provider" \| "prefix"` | catalog 声明；缺省 `prefix` | catalog 定义 → 生成物 | 只允许两个值，非法值在生成期即失败 |
| `threshold` | `number` | 触发比例，默认 `0.95` | `settings.json` | `0 < x < 1`，区间外拒绝加载 |
| `keepRecentTokens` | `number` | 保留尾部预算 | `settings.json` | 非负安全整数 |
| `k` | `number` | 重放的消息条数 | `compaction.ts` 由 `firstKeptEntryId` 派生 | `0 <= k <= previous.messages.length`，越界即 `prefix_mismatch` |
| `instruction` | `string` | 尾部 user 指令（首次摘要 prompt / 更新 prompt + `customInstructions` + `<previous-summary>`） | `compaction.ts` | 非空；不与前缀消息合并 |
| `ChatWireBody` | `{ api, messages, params }` | 真实 wire 请求 | `buildChatBody` | `messages` 只读；`params` 不含 `max_tokens` 覆盖 |

必填字段来源与构造责任：`k` 由切割点唯一决定（§2 已用探针钉住）；`instruction` 由既有 prompt 常量拼装，`previousSummary` 只拼进指令；`transport` 来自 catalog，coding-agent 不探测、不改写。

类型默认值也须符合业务值义：`transport` 缺省必须是 `prefix`（未声明即走前缀），不得因为字段缺失落到 `provider`。

## 9. 并发、异步、流式、事件、幂等与重试

- 并发：`lastRequest` 是单值字段，每轮覆盖；压缩与对话串行（`compaction.enabled` 检查在同一队列），不引入锁。
- 异步：`buildCompactionRequest` 同步纯函数；`completeSummarization` 保持现有 `retryAssistantCall`（指数退避）与 abort 语义。
- 流式：摘要请求仍走 `streamFn`/`completeSimple`，事件流由既有机制透传；UI 事件新增 `compaction_prefix_unavailable`（带 `reason`）。
- 幂等：`buildChatBody` 与 `buildPrefixRequest` 均为纯函数；重复构造不改变结果。重试复用同一 `requestOptions` 与同一请求体，重试不改变前缀。
- 队列：沿用现有自动压缩队列，不新增队列。

## 10. 错误语义与恢复流程

| 错误 | 触发条件 | 用户可见 | 恢复动作 |
|---|---|---|---|
| `PrefixUnavailable(no_previous)` | 无 `lastRequest`（冷启动、恢复会话、换模型） | `compaction_prefix_unavailable` 事件 | 序列化冷启动摘要 |
| `PrefixUnavailable(projection_drift)` | `k` 越界或当前投影前缀与上次不一致 | 同上 | 序列化冷启动摘要 |
| `PrefixUnavailable(prefix_mismatch)` | 两次 body 前 `k` 条字节不等 | 同上 | 序列化冷启动摘要 |
| `UnsupportedNativeCompaction` | catalog 声明 `provider` | `session_compact_failed`（含 `unsupported`） | 保留原上下文，不重试、不降级 |
| `length` / `error` | 摘要撞顶或 provider 报错 | `session_compact_failed` | 保留原上下文（沿用 `getSummarizationFailure`） |

`unsupported` 与 `PrefixUnavailable` 的区别是本设计的语义边界：前者是**能力声明后的显式失败**（AC5 要求不得静默降级到全价请求），后者是**前缀路径的合法降级**（AC6 要求走冷启动并可见）。

## 14. to-spec（方向合成）

- **Problem**：每次压缩的摘要请求与上轮请求零公共前缀，命中率 0%，长会话压缩成本是全价的 27–35 倍。
- **Solution**：压缩请求 = 上轮请求前缀 + 一条尾部指令；声明原生压缩的 provider 走原生路径，未实现时显式 `unsupported`；触发点统一为「95% 与模型限额先到者」。
- **Implementation decisions**：见 §6（两个 Module、一个 seam、两个 Adapter）与 §8（字段值义）。
- **Testing decisions**：§12；只跨公开 Interface，冷启动与降级各自有独立用例。
- **Out of scope**：`provider` Adapter 的真实原生调用、其它 provider 适配、跨模型迁移、tool-result pruner、`durable` 的 `reserveTokens`。
