# 压缩请求的前缀不变式

## 结论先行

pi 的压缩成本问题不是 provider 能力问题，是**请求构造**问题。锁定一条不变式，一行实现不用新增抽象：

> **压缩请求 = 上一次实际发给 provider 的 payload，尾部追加一条 user 指令。不得重新投影、不得换 system prompt、不得截断历史。**

实测（`deepseek-flash`，20129 字符前缀）：重放 + 尾部指令命中 **96.4%**，前缀中部改一个词则从改动点起全部失效。当前实现命中 **0%**。

## Module

**Module**：`packages/coding-agent/src/core/compaction/compaction.ts` 中的摘要请求构造（`buildSummarizationContext` 与其调用链）。

这不是一个新模块、新包或新接缝。它已经存在，只是把「请求长什么样」这件事编错了。

### 为什么不引入 summarizer 接缝

- **删除测试**：删掉一个 `Summarizer` 接口 + `DeepSeekSummarizer` adapter，复杂度不会散回调用方，只会回到这个文件。它是 pass-through。
- **One adapter means a hypothetical seam**：范围只有 DeepSeek，只有一个实现。开接缝就是给假想变体付接口税。
- **深度不来自抽象层**：换 provider 时要变的不是「谁来摘要」，而是「请求怎么拼」；后者是一条不变式，不是一组实现。

将来真要接 Anthropic 原生 `compaction`，那是**第二条不变式**（它压整段对话，没有 span 语义），届时应作为一次范围重划，而不是预先挖好接缝。

## Interface

调用方与测试都必须知道、且只有这些：

```ts
/** 上一次实际发往 provider 的请求体，按 provider 序列化后的最终形态捕获。 */
interface SentRequest {
  readonly messages: readonly unknown[];
  readonly tools: readonly unknown[];
  readonly params: Readonly<Record<string, unknown>>;
}

/**
 * 构造一次摘要请求。保证返回值与上一次请求共享逐字节相同的前缀，
 * 且只在尾部追加一条 user 指令。
 *
 * @throws PrefixUnavailable 上一次请求不可用（会话刚从磁盘恢复、或捕获缺失）
 */
function buildSummarizerRequest(
  previous: SentRequest | undefined,
  instruction: string,
): SentRequest;
```

接口里必须写清的四个事实（invariants，不只是类型）：

1. **不变式**：`result.messages` 的前 `previous.messages.length` 项与 `previous.messages` 深度相等；`result.tools`、`result.params` 与 `previous` 相等；新内容只出现在末尾的 user 消息。
2. **时序约束**：`previous` 必须是**最近一次成功发出的**请求。任何改变更早条目的操作（`context_edit`、section 补丁在 `deepseek-flash` 上的折叠、工具集变化）都会让 `previous` 不再有效。
3. **错误模式**：只有一个 —— `PrefixUnavailable`。摘要本身失败沿用既有的 `session_compact_failed`，不新增码。
4. **性能特征**：命中比例等于 `previous` 在 provider 侧已持久化的长度；尾部指令（上限 300 token）永远按未命中计价。

## Implementation

### 捕获点

`SentRequest` 必须在 **provider 序列化之后**捕获，即在 `openai-completions` 的 `convertMessages()` 与 `resolveTranscriptTools()` 之后，而不是在 transcript 层。

理由：`deepseek-flash` 走 `collapseSystemMessages`（`packages/ai/src/utils/transcript.ts:105`），把中途 system 消息折叠进首条；`deepseek-v4-pro` 不折叠。两者在 transcript 层看起来相同，在 wire 层不同。捕获 wire 形态，前缀计算就与投影无关——这是本设计唯一需要「藏起来」的复杂度。

`packages/ai` 只需多暴露一个只读的「上一次请求体」句柄；不新增能力位、不改 provider 接口。

### 构造

```
result.messages = [...previous.messages, { role: "user", content: instruction }]
result.tools    = previous.tools
result.params   = { ...previous.params, max_tokens: <summary cap> }
```

不做的事：不换 system prompt、不 serialize、不截断 tool result、不重排消息。

### 失效与降级

| 情形 | 处理 |
|---|---|
| 会话从磁盘恢复，无 `previous` | 抛 `PrefixUnavailable`，调用方按现有路径做一次冷摘要，并在 UI 标注「本次摘要未命中缓存」 |
| 上次请求之后有 `context_edit` / section 补丁 / 工具变化 | `previous` 仍有效（它记录的是**已发出**的形态），但它的末条消息可能已不在当前 surface 上——只有当它仍是当前 surface 的连续前缀时才可用；否则抛 `PrefixUnavailable` |
| `previous` 存在但摘要调用失败 | 不重试压缩，走 `session_compact_failed` |

保留旧的 serialize 路径，**只**作为 `PrefixUnavailable` 的冷启动分支。它不是第二个摘要实现，是同一个函数的 fallback 分支：一个入口、两条分支，不需要接缝。

### 测试面

接口就是测试面。三条断言钉住边界：

1. 给定 `previous`，构造出的请求其 `messages` 前 N 项与原数组深度相等（字节前缀）。
2. `tools` 与 `params` 不被改写（除 `max_tokens`）。
3. `previous === undefined` 时抛 `PrefixUnavailable`，且 fallback 分支不产生 system prompt 之外的额外消息。

失败测试草案见 `.scratch/prefix-invariant.test.ts`。

## 与 codebase-design 的自检

- **Interface 是否比实现小**：是。四个事实 + 一个函数，实现要处理捕获点、wire 形态、失效判定。
- **测试是否只跨接口**：是。断言全部落在 `buildSummarizerRequest` 的返回值上，不需要知道捕获点在哪。
- **Locality**：前缀规则只活在一个函数里；`deepseek-flash` 的折叠差异被吸收在捕获点，不外泄。
- **Leverage**：同一处修复同时作用于自动压缩、`/compact`、溢出恢复三条路径，因为三者都经过这个构造。

## 未决

- `max_tokens` 取摘要上限时是否会影响前缀命中：实测 C 组显示尾部段不计入命中，因此可安全覆盖。
- `deepseek-v4-pro` 未在本设计中单独实测；其折叠行为不同（补丁追加为中段 system），但因为捕获点在后，不变式对它同样成立。等有额度时补一组对照（保留在 map 的 fog 之外，属于执行期验证）。
